# Оценка проекта Poker

## TL;DR
- **Общая оценка:** **6.5/10** для MVP.
- Проект уже покрывает ключевой сценарий: серверный цикл раздачи, SignalR-взаимодействие и клиент на WPF.
- Для перехода к production-уровню не хватает автотестов, полноценной обработки all-in/side-pot и базовой эксплуатационной инфраструктуры (логирование, health-check, метрики).

## Что сделано хорошо
1. **Чистое разделение на слои** (`Poker.Core`, `Poker.Domain`, `Poker.Shared`, `Poker.Client.Wpf`) — удобно развивать отдельно домен, транспорт и UI.
2. **Сервер — source of truth**: игровой стейт централизован в hub/core, что снижает риск рассинхронизации клиентов.
3. **Реализована валидная базовая покерная механика**: блайнды, улицы, turn progression, showdown, базовый hand evaluator.
4. **Неплохая читаемость для MVP**: логика компактна, нет сложной инфраструктуры, легко вкатиться в код.

## Основные риски и ограничения

### 1) Неполная покерная математика (критично для честной игры)
- В коде явно указано, что showdown сейчас **без side pots**.
- Это означает некорректные выплаты при нескольких all-in с разными стеками.
- В таком виде продукт подходит для демо/прототипа, но не для серьёзной игры на фишки/деньги.

### 2) Отсутствие тестового контура
- В репозитории не видно unit/integration-тестов для `GameEngine` и `HandEvaluator`.
- Для доменной логики покера это ключевой риск: регрессии здесь очень дорогие.

### 3) Сетевой и эксплуатационный минимум
- Сервер запускается как простой SignalR endpoint без health/readiness endpoint'ов.
- Нет структурного логирования и мониторинга (ошибки сейчас mostly через `Console.WriteLine`).

### 4) Пакетная согласованность
- В WPF-клиенте указан пакет `Microsoft.AspNetCore.SignalR.Client` версии `10.0.2` при `net8.0-windows`.
- Стоит проверить совместимость по runtime/pacakge policy (обычно лучше держать согласованную major-версию с серверным стеком).

## Что рекомендую сделать в первую очередь (план на 2–3 итерации)

### Итерация 1 (обязательная)
1. Добавить unit-тесты для:
   - категорий рук (все от High Card до Straight Flush),
   - tie-break правил,
   - переходов улиц,
   - fold/check/call/raise кейсов,
   - all-in сценариев.
2. Вынести и покрыть тестами расчёт банка (пока без side-pot — зафиксировать контракт тестами).
3. Добавить `README` с запуском сервера/клиента и описанием ограничений движка.

### Итерация 2 (критично для качества игры)
1. Реализовать **side-pot** и протестировать сложные multi-all-in раздачи.
2. Добавить валидацию входных DTO (пустые имена, отрицательные ставки, invalid room id и т.д.).
3. Добавить устойчивость к повторным подключениям (reconnect/rejoin semantics).

### Итерация 3 (production hygiene)
1. Включить структурное логирование (например Serilog).
2. Добавить health-check endpoint и базовые метрики.
3. Продумать персистентность столов/сессий (сейчас состояние в памяти процесса).

## Продуктовая оценка
- **Для учебного проекта / демо:** отлично.
- **Для закрытого MVP с друзьями:** приемлемо с оговорками.
- **Для production:** рано, пока не закрыты тесты и side-pot.

## Оценка по осям
- Архитектура: **7/10**
- Читаемость и поддерживаемость: **7/10**
- Корректность доменной логики: **6/10**
- Готовность к нагрузке/эксплуатации: **5/10**
- Тестопригодность и QA-покрытие: **4/10**

**Итог:** хороший фундамент для покерного MVP; следующий большой шаг — формализовать правила деньгами (side pots) и зацементировать поведение автотестами.
